## Operational problem
Before any agent can be given production access (G2.3B onward), the repository lacks
trustworthy foundations: the deployed build identity is **fake** (`version.js` is
hardcoded frozen `v2.5.0` / `2025-12-16`, `isFrozen: () => true`); there is no
`build-info.json`; the Hostinger deploy tooling is **not on the release line**
(only a library `deploy-lib.mjs` exists on feature branches, with no CLI, no
dry-run, and an undeclared `tus-js-client` dependency); `DEPLOYMENT.md` is stale
(Vercel/Netlify/theventguys, not Hostinger/`app.bhfos.com`); and there is no secret
inventory, migration-verification tool, synthetic-data registry, health probe,
branch-protection verifier, or live Release Baton/Ledger. Without these, later
phases cannot verify what is deployed, roll back safely, or record what happened.

## Proposed correction (repository-only)
Implement the smallest coherent set of repository foundations (17 files; see brief
Section 6): real build identity + generated `dist/build-info.json` and a verifier;
corrected `DEPLOYMENT.md`; the Hostinger deploy tooling on the release line with a
mandatory **non-mutating `--dry-run`** CLI; a **names-only** secret inventory; a
**read-only** migration-state verifier; a synthetic-data registry **structure**; a
minimum **health probe**; a **read-only** branch-protection verifier; and the live
Release Baton and Release Ledger. **Nothing is executed against production.**

## What changes
- Build identity becomes real and inspectable (in the app diagnostics surface and

- Readiness artifacts (secret inventory, migration verifier, synthetic registry,
  health probe, branch-protection verifier, Baton, Ledger) exist and are

## What does NOT change

- No credentials provisioned; no secret **values** enter the repository.
- No migrations run; no production data touched; no external platform mutated.
- No monitoring/infrastructure buildout, no workflow redesign, no application
  redesign, and no G2.3B-E work.

## Deployment plan
**No deployment.** The deploy CLI defaults to non-mutating and is validated in
**dry-run only**; a mutating upload requires explicit environment + authorization
inputs and is not reachable through normal validation. Real deployment authority is
a separate G2.3C decision.

## Rollback plan
Clean `git revert` of the G2.3A PR(s). Repository-only: zero runtime, data,
credential, or production impact. Rollback point = pre-merge `main` SHA, recorded on
the Baton.

## Known limitations
- `deploy-hostinger-static.mjs` does not exist yet and must be **created** (the
  umbrella brief assumed it existed in `tmp/`); `tus-js-client` must be declared.
  This is additive work, still repository-only, defaulting to non-mutating and
  dry-run-gated.
- The feature-branch `deploy-lib.mjs` is **source material for review only** - not
  approved code and not automatically eligible for copying to `main`. It must pass
  complete Builder and Architecture Guard inspection of all network operations,
  credential loading/masking, local/remote paths, TUS upload, overwrite/deletion,
  retry/partial-failure, archive creation/retention, target-environment checks,
  SHA/release-identity checks, dry-run behavior, and rollback assumptions before any
  version reaches the release line.
- **No server-side rollback capability is claimed unless independently verified.**
  Retained local archives are the only confirmed rollback affordance today.
- Live branch-protection enforcement and remote migration state cannot be fully
  verified from the repository alone; the verifiers report exactly what they can
  and cannot confirm, with the remainder deferred to the G2.3B read-only
  diagnostics phase.
- The existing `BRANCH_PROTECTION.md` omits `CI / identity_contracts`; the update
  closes this gap.

exist. After implementation, green checks, and completed independent Architecture
Guard review, a **new consolidated Decision Packet** will identify the **exact PR
and head SHA** and request **one final merge authorization**. The Release Agent may

customer-communication actions each require their **own** separate explicit
authorization and are not implied by any approval above._
