# Decision Packet - G2.3B-B2B Supabase I2 Credential Issue (post capability verification)

> **Separate packet.** No credential is issued by this document alone.
> Evidence: `command-center/docs/governance/SUPABASE_I2_CAPABILITY_VERIFICATION.md`
> (G2.3B-B2A verification — no live token created).

---

## Release
- **Release ID:** `G2.3B-B2B` / `v2.2`
- **Risk tier:** **Tier 3**
- **Prerequisite:** G2.3B-B2A Founder authorization (GitHub App + Hostinger blocked +
  Supabase verify-only); capability verification complete
- **Architecture Guard:** Required + access review before issue

## Operational problem
I2 needs least-privilege Supabase diagnostics access. PATs and generic Dashboard
Read-Only membership are prohibited. Capability verification shows only **OAuth2
app tokens** honor fine-grained Management API permissions — and two candidate
read permissions still enable sensitive surfaces (`analytics_logs_read` → log SQL
including postgres/edge logs; `edge_functions_read` → deployed function **body**).

## Proposed correction
Authorize **at most one** of the issue options below (A, B, or C). Do not issue a
PAT, Dashboard Read-Only member, service-role key, or account-wide credential.

## Exact identity (all options)
| Field | Value |
| --- | --- |
| Credential type | **OAuth2** Management API app token (officially supported fine-grained mechanism) |
| Inventory name | `I2_SUPABASE_OAUTH_DIAGNOSTICS_TOKEN` (names only) |
| Scope | Production project only (authorize app only against production org/project) |
| Lifetime | Short-lived access token + refresh until revoked (platform-controlled) |
| Storage | Secret store category only |
| Audit | OAuth app identity (not founder-personal PAT) |
| Revocation | Revoke OAuth app authorization; rotate app client credentials |
| Explicitly prohibited | PAT; Dashboard Read-Only member; service-role; `secrets:*`; `database_read`; `database_write`; `edge_functions_write`; Auth-user browsing; config mutation |

## Issue options (choose one)

### Option A — Minimal (recommended first issue)
| Field | Value |
| --- | --- |
| Permissions | `projects:read` / `projects_read` only |
| Enables | Project metadata, service health, non-secret project status |
| Does not enable | Logs, function inventory/body, SQL, secrets, writes |
| B3 negative tests | Attempt secrets list, SQL run, function deploy, `/functions/.../body` → expect denial |

### Option B — Add function inventory (accepts source-body risk)
| Field | Value |
| --- | --- |
| Permissions | Option A **plus** `edge_functions_read` |
| Enables | List/get function metadata **and** `GET .../functions/{slug}/body` (platform-enforced; cannot split) |
| Founder must accept | Deployed Edge Function **source body** is technically readable |
| Operational rule | Do not call `/body` in routine I2; still not a technical control |
| B3 negative tests | Attempt `edge_functions_write` paths and secrets/SQL → expect denial; record whether `/body` succeeds (expected yes if granted) |

### Option C — Add analytics logs (accepts sensitive log risk)
| Field | Value |
| --- | --- |
| Permissions | Option A or B **plus** `analytics_logs_read` |
| Enables | Unified log query API including `postgres_logs` / `edge_logs` via ClickHouse SQL |
| Founder must accept | Sensitive production log content is technically readable; masking is operational only |
| B3 negative tests | As above; confirm secrets/SQL Editor/database_read still denied |

### Explicitly not offered
- `database_migrations_read` — partner-gated endpoint; unavailable unless separately proven
- `database_read` — enables SQL execution surfaces — **forbidden**
- Schema/table metadata requiring `database_read` — **defer to B4**

## Access granted
Only the single option the Founder authorizes (A, B, or C). Names-only inventory
update after issue.

## Access not granted
Hostinger I2; GitHub beyond B2A; B3–B5 campaigns; deployment; migration;
financial/customer/destructive actions; any secret values in repo/chat/Markdown.

## Risk classification
Tier 3

## Evidence completed
`SUPABASE_I2_CAPABILITY_VERIFICATION.md`: PAT all-or-nothing; OAuth2 is fine-grained
path; `edge_functions_read` includes body; `analytics_logs_read` includes sensitive
logs; secrets/SQL/writes excluded when those permissions omitted.

## Blocking findings
None that prevent **choosing Option A**. Options B/C require explicit acceptance of
non-excludable sensitive read surfaces.

## Known limitations
OAuth2 is designed as an integration flow; first-party I2 must still use OAuth2
(not PAT) to obtain FGA. Migration list may remain unavailable without partner
entitlement.

## Rollback / revocation
Revoke OAuth app authorization; delete/rotate client credentials; mark inventory
name revoked.

## Recommendation
Authorize **Option A only** first (`projects:read` / `projects_read`). Defer
`edge_functions_read` and `analytics_logs_read` until Founder explicitly accepts
body and sensitive-log exposure (or a gateway/masking control exists).
