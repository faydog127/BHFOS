## 1. Objective (one problem) — North Star

**Problem:** BHFOS has no proportional operating model for *production operations*.
Today, deployment mechanics, diagnostics, log analysis, incident response, and
environment maintenance either stall or are relayed back to the founder. This
consumes Founder Focus and Energy and slows safe delivery.

**Governing objective (North Star):**
> Protect Founder Focus and Energy while allowing safe, useful development and
> production operations to move quickly.

The model must ensure:

- governance is **proportional to actual risk**;
- agent roles are **available capabilities, not a mandatory assembly line**;
- agents complete **authorized mechanical work** instead of returning it to the founder;
- the founder makes **business and risk decisions**, not technical deployments, debugging, log analysis, or environment maintenance;
- routine releases normally require **one consolidated founder decision**;
- **repeated approval requests for an unchanged release are prohibited**;
- technical work is **not relayed manually between chats** by the founder;
- **process burden must not exceed** the risk or complexity of the change.

## 8a. New production role intent (specification the Builder will codify)

### 8a.1 Production Operator (authorized mechanics)
Eventually able to perform, **only within a specific release/incident
authorization**: deploy an approved commit; verify deployment identity; bounded
production smoke testing; explicitly authorized migrations; health verification;
predefined rollback; approved synthetic-data creation and cleanup; release
reporting. Never self-authorizes; never touches real customer/financial data
except as an explicitly authorized action.

### 8a.2 Production Diagnostics (primarily read-only)
Eventually able to perform: deployment-log inspection; application-log
inspection; Supabase and Edge Function diagnostics; authentication diagnostics;
database and migration-state inspection; environment and build-identity
verification; browser/network-error diagnosis; incident evidence collection;
rollback-versus-forward-fix recommendation. **Read-only by default**; any write
requires separate explicit authorization.

### 8a.3 Production Incident Commander
Activates for **P0, P1, and qualifying P2** incidents. Assigns severity;
establishes deployed and known-good states; pauses conflicting releases;
coordinates Diagnostics and Production Operator; chooses containment, rollback,
or bounded forward repair; requests a Builder hotfix when needed; maintains one
response plan; minimizes founder interruption; verifies recovery; closes the
incident; returns the system to normal release governance.

## 8b. Controlled production UAT model (update to `independent-uat.md`)

Independent UAT must **not** remain completely excluded from production. G2.2
plans a minimum update to `command-center/.cursor/agents/independent-uat.md` so
Independent UAT **may perform controlled production workflow testing only when
all** of the following hold:

- the exact release and deployed SHA are identified;
- the Release Baton **explicitly authorizes production UAT**
  (`production_test_authorization`);
- the exact route, role, workflow, and test scope are identified;
- a dedicated **least-privilege production test identity** is used;
- only **registered synthetic records** are accessed;
- no unrelated or real customer records are opened;
- no real financial records are accessed;
- no customer communications are sent;
- no payment, refund, invoice, security, permission, or destructive action is performed;
- no secrets are exposed;
- actions and results are **logged**;
- **cleanup authority is explicitly defined**;
- the agent **stops** when the environment, identity, record, or scope differs.

Constraints:

- **Production UAT access must not be self-authorized.**
- **Preview or test environments remain preferred** when they can prove the
  required acceptance criteria.
- Production UAT exists to **independently verify the deployed workflow**, not to
  debug, administer, or maintain production.

This is additive: the existing human-operated-production language and all existing
UAT verdicts (`PASS/FAIL/PARTIAL/BLOCKED/UNVERIFIED/NOT_APPLICABLE/
OWNER_CONFIRMATION_REQUIRED`) are preserved.

## 9. Risk-tier model (to codify in `OPERATING_MODEL_v2.2.md`)

Governance is proportional to risk. **Not every release needs every agent.**

| Tier | Definition | Minimum required path |
| --- | --- | --- |
| **Tier 1** | Low-risk UI, content, tests, documentation, bounded corrections. | Orchestrator brief (may be 1 paragraph) → Builder PR → **a different chat** confirms → owner one-click accept → Release Agent merge. Independent review optional; UAT lightweight. |
| **Tier 2** | Operational workflows, shared components, scheduling, inspections, intake, other meaningful user behavior. | Orchestrator brief → Builder PR → Architecture Guard review → Independent UAT (USABLE) → owner checkpoint → Release Agent merge → deploy under authorization. |
| **Tier 3** | Authentication, authorization, tenant isolation, migrations, money-loop behavior, secrets, financial actions, customer communication, destructive data operations. | Full chain + `review:gate` trigger-domain gate + explicit written owner approval for migrations + Decision Packet + Production Operator deploy under separate authorization + drift check + rollback point recorded. |

Tier is assigned by the Orchestrator at planning time and recorded on the Release
Baton. Trigger domains (`tenant_isolation`, `money_state`, `acceptance_commit`,
`state_machine`, `completion_gate`) force Tier 3 regardless of surface size.

## 10. Founder Focus & Energy, interruption protocol, Founder Burden stop

**Founder Focus and Energy operating rules (codify in `OPERATING_MODEL_v2.2.md`):**
- The founder makes business and risk decisions, not technical mechanics.
- The founder is not asked to run commands, inspect logs, manage credentials,
  relay technical messages between chats, or perform deployment mechanics.
- One consolidated decision per routine release.
- One unchanged release must not produce repeated approval requests.

**Interruption protocol:**
- **P0 / P1:** may interrupt immediately (including quiet hours).
- **P2:** interrupts only when business judgment or extraordinary authority is
  required; otherwise batched.
- **P3 / routine releases:** batched into one Decision Packet.
- **Quiet hours:** broken only for defined critical conditions (P0/P1 or a
  documented critical drift/security condition).

**Founder Burden stop condition:**
- If an agent finds itself about to hand the founder mechanical/technical work
  (commands, logs, credentials, message-relaying, deployment mechanics), it must
  **STOP**, record the burden as a blocker on the Release Baton, and route the
  mechanical work to the correct agent role instead of the founder.
- If the same release triggers a repeat approval request with no material change,
  that is a Founder Burden condition — HALT and consolidate rather than re-ask.

## 14. Incident model (to codify in `INCIDENT_AND_PRODUCTION_READINESS.md`)

Severity:

- **P0:** Security exposure, possible corruption, or business completely unavailable.
- **P1:** Core money or operational workflow unavailable.
- **P2:** Important degradation with a workable fallback.
- **P3:** Minor defect handled through normal stabilization.

For each severity, codify: activation criteria; interruption rules (per §10);
containment authority; rollback authority; escalation conditions; **time-boxed
decision expectations**; recovery criteria; incident closure; and **when a
post-incident review (learning) is actually required** (default: required for
P0/P1 and any P2 that required a rollback; optional otherwise). **Incidents must
restore service before improvement or redesign.**

## 15. HALT and consolidate policy (to codify in `OPERATING_MODEL_v2.2.md`)

HALT is a **governance command, not a fictional technical kill switch.**

When HALT is issued:
- no new commits, merges, deployments, migrations, or production mutations;
- active roles record their exact stopping state (on the Release Baton);
- the coordinator consolidates **one** Decision Packet;
- work resumes only after explicit authorization.

**Future technical emergency-brake capabilities (documented as future, not built):**
cancel active workflows; pause deployments; revoke credentials; disable scheduled
production actions. These require the later controlled implementation.
