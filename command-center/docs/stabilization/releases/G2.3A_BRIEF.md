## 1. Purpose

G2.3A establishes the repository-side foundations required **before** any agent is
given production access. Its purpose is to make **release identity, deployment
tooling, readiness evidence, and operational records trustworthy and
inspectable** - entirely within the repository.

Per umbrella brief Section 9, G2.3A is the prerequisite for every later phase: it
produces the build identity, deploy tooling on `main`, inventories, synthetic-data
registry structure, health signal definition, branch-protection verification, and
the live Release Baton and Release Ledger that G2.3B-E depend on.

**This phase remains entirely repository-only. No production access.**

| Build metadata can be generated without exposing secrets | SHA / merge SHA / timestamp / release id / environment come from git and CI context, not from `.env`. `tools/build-production.mjs` already enforces a `VITE_` allowlist and runs `tools/scan-dist-for-secrets.mjs` after build. |
| No `build-info.json` exists | No `build-info` reference anywhere except the umbrella brief. |
| CI builds without `.env` | `.github/workflows/ci.yml` `build` job runs `npm run build:local` (= `vite build`); `npm run build` (`tools/build-production.mjs`) requires a production `.env` and is not used by CI. |

**Design implication:** build-info generation must be wired so that **`build:local`
(the CI build path) also emits `dist/build-info.json`**, otherwise the umbrella
brief evidence threshold ("CI-DEPLOYED build artifact showing the real SHA")
cannot be met without a production `.env`.

**Fields to surface** (deployed commit SHA; merge SHA where available; build
timestamp; release identifier; environment; migration version; frontend asset
version). SHA/merge SHA/timestamp are derivable in git and GitHub Actions;
`environment` is set by the build path; `migration version` is derivable from the
latest `supabase/migrations` filename; `frontend asset version` from the built
index/asset hashes. Where a value is unavailable (e.g. merge SHA on a feature
build) it must be emitted as an explicit `unknown`, never faked.

**Recommendation:** generate `build-info.json` in `dist`, and surface build
identity in **both** the application diagnostics surface (existing
`SystemDiagnostics.jsx`, replacing the frozen label as build truth) **and** the
static `build-info.json` (machine-readable for the health probe and drift checks).

**Deploy-library source-material status (binding):** the feature-branch copy of
`deploy-lib.mjs` (commit `84576c3`) is **source material for review only**. It is
**not approved code**, is **not automatically eligible for copying to `main`**, and
is **subject to complete Builder and Architecture Guard inspection** before any
version of it is committed to the release line. Nothing about its current presence
on feature branches grants it entry to `main`.

**Implementation must independently verify (not assume) all of the following** in
whatever code is proposed for `main`:

- all network operations (which endpoints are called, when, and under what
  conditions);
- credential loading and masking (`HOSTINGER_API_TOKEN` read from env only; never
  logged, printed, or written to any artifact);
- local and remote paths (source `dist`, staging, and `public_html/` targets);
- TUS upload behavior (chunking, resumption, fingerprinting, cleanup);
- overwrite and deletion behavior (what is overwritten or removed on the host);
- retry and partial-failure behavior (idempotency and safe failure);
- archive creation and retention (what is retained locally and where);
- target-environment checks (correct domain/app before any mutation);
- SHA and release-identity checks (intended SHA present and matched);
- dry-run behavior (proves zero network mutation);
- rollback assumptions (see caveat below).

**Mutation-safety requirements (binding):**

- The production deploy CLI (`deploy-hostinger-static.mjs`) must **default to
  non-mutating behavior**.
- A mutating upload must require **explicit environment and authorization inputs**
  and must **not be reachable accidentally through normal validation commands**
  (e.g. `--dry-run`, `verify`, `health-probe`, or any CI/lint/build step).
- Each mutating call in `deploy-lib.mjs` must be guarded so it is **unreachable in
  dry-run** and unreachable without the explicit mutation inputs.

**Rollback claim caveat (binding):** **no server-side rollback capability may be
claimed unless it is independently verified.** The current library retains local
`dist-deploy-*.zip` archives but has no verified server-side previous-release
preservation; the corrected documentation and any rollback statement must not
assert more than what is independently confirmed.

**Validation required before the (later, separate) merge to `main`:** (a) the
mandatory non-mutating `--dry-run` CLI exists and proves zero network mutation;
(b) `tus-js-client` is declared in `package.json`; (c) dry-run stages/validates the
archive and prints the intended SHA + environment without calling any Hostinger
mutation endpoint; (d) every mutating call is guarded per the mutation-safety
requirements above; (e) Architecture Guard has reviewed all deploy-tool areas
listed in Section 9. **The deployment tool is not executed in G2.3A.**

## 8. Detailed component designs (planning only)

### 8.1 Secret inventory structure (names only)

Markdown table in `SECRET_INVENTORY.md`. Columns:

`name` | `owning system` | `purpose` | `environment` | `expected storage
location` | `owning human/role` | `rotation requirement` | `revocation method` |
`currently verified?` | `notes (non-sensitive)`.

**Never** contains: secret values, tokens, passwords, service-role keys,
connection strings, private keys, or raw `.env` contents. It records that (for
example) `HOSTINGER_API_TOKEN` exists, is owned by the founder, is used by the
deploy tool, is stored in the operator's local env / secret store, and how it is
rotated/revoked - **by name only**.

### 8.2 Migration-verification design (read-only)

`verify-migration-state.mjs`:

- **Defaults to read-only**; never applies migrations; never edits migration
  files.
- **Local evidence (always):** enumerate `supabase/migrations/*.sql`, verify
  timestamp-prefix ordering, detect duplicate/missing version prefixes, flag
  edits to already-applied (immutable) migrations where a ledger exists.
- **Remote evidence (only if linked access is present):** compare against
  `supabase migration list --linked`. If linked access is unavailable, **stop the
  remote comparison and clearly report "remote state not checked"** - do not fail
  silently and do not guess.
- **Clearly distinguishes local evidence from remote evidence** in output.
- **Never exposes credentials.**
- **Output:** machine-readable JSON plus a human-readable summary.
- **No Supabase access occurs during planning or during G2.3A implementation
  validation** (offline behavior is what is validated in A).

### 8.3 Synthetic-data registry design

Repository structure only (no records created):

- `SYNTHETIC_DATA_REGISTRY.md` - purpose, rules, lifecycle, cleanup authority.
- `synthetic-data-registry.template.yaml` - schema + one clearly-marked example
  entry.
- Optional `validate-synthetic-registry.mjs` - schema validation.

Record types covered: synthetic user; lead/customer; property; inspection;
appointment; job/work order; estimate; invoice; **payment simulation or
non-financial substitute**.

Per-record fields: `record type` | `identifier` | `tenant` | `purpose` |
`creator role` | `release/incident reference` | `created timestamp` | `cleanup
status` | `cleanup authority` | `protected-from-cleanup flag` | `non-sensitive
notes`.

Synthetic-only; registered; never mixed with real data; no customer contact; no
live charges. **No real or synthetic production records are created in G2.3A.**

### 8.4 Minimum health-probe design

`health-probe.mjs` (smallest useful):

- Frontend reachable (app shell returns 200).
- Expected `build-info.json` reachable and parseable.
- Deployed SHA available from `build-info.json`.
- Application shell loads (root asset refs return 200 - can reuse the asset-check
  logic from `deploy-lib.mjs`).
- **Optional** Supabase connectivity signal that returns only reachability, never
  data (e.g. an unauthenticated REST endpoint status), guarded so it is skipped if
  not configured.
- Explicit timeout and failure behavior; non-zero exit on failure.
- Machine-readable JSON output.
- **No authentication bypass; no destructive behavior.**
- **Testing without production:** point the probe at a local `vite preview` /
  `build:local` output served statically (or a preview URL). The probe must not
  require production access during implementation validation.

### 8.5 Branch-protection verification design

Combination of documentation + read-only script:

- **Repository-derivable (no API):** target branch is `main`; expected required
  checks are `CI / lint`, `CI / identity_contracts`, `CI / build`,
  `Ledger Lock / ledger_lock` (from `.github/workflows/`); `.github/CODEOWNERS`
  presence; intended policy (`BRANCH_PROTECTION.md`).
- **Requires GitHub API (`gh api repos/:owner/:repo/branches/main/protection`):**
  actual enforcement of required checks, required reviews, force-push
  restrictions, deletion restrictions, dismiss-stale-reviews, conversation
  resolution.
- **Unknown until the later read-only diagnostics phase (G2.3B):** org-level
  overrides, actor bypass lists, and anything requiring elevated GitHub scopes.
- `verify-branch-protection.mjs` is read-only and **reports** the live state;
  when API access is absent it **prints exactly what it could and could not
  verify** and exits accordingly - it never modifies GitHub settings.

### 8.6 Baton and Ledger initialization

From `RELEASE_BATON.template.yaml` and `RELEASE_LEDGER.template.yaml`:

- **Baton** `command-center/docs/governance/RELEASE_BATON.g2-3.yaml`:

  Sections 10-12), `governance_version: v2.2`, `risk_tier: Tier 1` for the current
  A phase, `release_brief_path` pointing at the umbrella + A briefs, `current_owner`
  Orchestrator, `pr_number`/`base_sha`/`head_sha` filled once known, authorization
