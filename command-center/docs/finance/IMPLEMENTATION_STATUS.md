## Unresolved

- A broader accounting-restatement workflow is not built. Factual corrections update the row in place. That is an accepted limitation for this release.
- Schema version 1 still has no declared monthly check-in series. Plan and Variance stay `--`. Stage scenario revenue is not a monthly basis. Version 2 is `docs/finance/MONTHLY_PLAN_BASIS_CONTRACT.md`, stored only through `20261003180000_finance_plan_monthly_basis.sql`. That migration is not applied on any remote project. New blank plans are version 2 so they can carry a monthly basis. An existing version 1 draft still upgrades in place.
- Deviation — blank plan schema. Packet item 4 describes open-draft behavior. `createBlankPlan` previously inserted schema version 1. The correction inserts schema version 2 with `{ ...blankPlanInputs(), monthly_basis: {} }` through the existing validator. No new migration and no new financial meaning. The first approved plan created in the UI is therefore an empty version 2 map: check-in shows the partial-basis sentence and `--`, not the version 1 “no monthly basis” sentence. Version 1 `--` remains covered by `plannedFactsForMonth` and the SQL tests.
- The database still accepts, approves, and copies a version 2 plan whose inputs are only `{monthly_basis:{}}`. The Finance screen now validates on load with `storedPlanDecision` before it reads `inputs.stages`. An invalid stored document clears the open plan and shows `A stored plan failed validation. An administrator must repair the draft.` The code is `finance_schema_unsupported`. The screen does not echo or log the document. A structural-key database check was not added. Recommendation, not done: a new migration (not an edit of `20261003180000`) could require `structural`, `stages`, `staffing`, `owner_field_replacement`, `cost_pools`, `channels`, and `services` on version 2 after `monthly_basis` is present. That check would also reject the minimal documents in SQL test 06. The challenge file that demonstrates the gap is reference only and is not a suite test.
- JavaScript monthly amounts of 21 or more whole digits are rejected, matching `numeric(14,2)` and the existing hour bound. `String(1e21)` is `1e+21`, so the digit counter treats `>= 1e21` as too large. Month key `0000-01-01` is still accepted by both the JavaScript month pattern and the database pattern. Tightening it needs a new migration, so it is a known limitation. Both sides also accept `-0`. That value is harmless and was left unchanged.
- The monthly-basis editor keeps the typed text until blur or save. Typing `10.5` and `10.05` no longer collapses to `105`.
- After a check-in version conflict, New month returns immediately, the same way a history click does. It does not clear the conflict or load another form. Save still returns `version_conflict`. Reload still replaces the form from the server row.
- A numeric-string appointment price makes the whole scheduled-price series unavailable. `finiteAppointmentPrice` accepts only a finite number. That is safe and coarse. The behavior was not changed.
- Accepted note: referral `commission_amount || 0` still accumulates a dead field. Only `referrals` is charted. It is not a Finance metric. The line was not changed.
- Accepted note: `finance_plan_before_insert` forces draft status, version 1, and the acting user. It does not freeze `schema_version`. The update trigger freezes schema except the `schema_upgrade` branch. The insert trigger was not changed.
- Who applies a migration to staging or production is not this stage. This stage does not apply the migration remotely.
- The Preview Supabase host still cannot be identified from the repo. Writes stay disabled there unless a build sets `VITE_FINANCE_SYNTHETIC_ONLY=approved-synthetic`.
- `version_conflict` is also returned when row level security hides the row. The client does not distinguish a hidden row from a stale version.
- After a check-in `version_conflict`, Save stays blocked until Reload. Reload loads the latest server row and replaces the form with that row. Unsaved edits are discarded. There is no merge. Choosing a history month, or New month, while the conflict is open does not clear it and does not load another form. The plan editor's own Reload already replaces plan inputs from the server.
- The Playwright check-in spec is not part of CI. It needs a freshly reset local database. The spec types `10.50` into the monthly basis and expects a partial basis on both the empty first plan and the later month that stores that amount.
- Referral partner commission totals still coerce a missing `commission_amount` with `|| 0`. That figure is not charted and is not a Finance metric. Accepted as recorded above.
- `finance.plan_transition` can be set by direct SQL in the same session, the same way `approve` already could. The app does not set it except inside the approve and upgrade functions.
